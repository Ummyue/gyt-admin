## 1. 业务定位

**v1.2.0 把编排页改成两步向导**，并把「属性编辑」从常驻侧栏改为右侧抽屉。

| v1.1.0 的问题 | v1.2.0 的处理 |
|---|---|

## 5. 步骤 2：流程设计（画布）

### 5.1 画布布局

- **满宽展开**：不再有右侧常驻属性面板，画布宽度 = 内容区全宽
**v1.6.0：画布整页铺满 + 节点自上而下纵向排列**

- 画布**铺满页面剩余高度**（不再是一个固定高度的小框）：进入步骤 2 时给
  `.page-body` 加 `is-canvas` 类（`overflow: hidden !important` + flex 布局），
  滚动交给画布自身 `overflow-y: auto`
- 节点卡片 **420px 宽，纵向单列**，`align-items: center` 居中，top 依次递增
- 连接线为**竖向细线**（`1px × 34px`，底部带向下箭头），中间一个 `+` 圆形按钮
- 节点卡左侧色条（`border-left: 3px`），带触发条件的节点底色为浅琥珀 `#FFFBEB`

### 5.2 插入节点：选项卡片

点击连接线上的 `+`，在该连接线**正下方**弹出选项卡片（220px 宽，白底圆角阴影）：

**v1.6.0：插入选项聚合为单一「审批节点」**

| 顺序 | 选项 | 图标色 | 说明 |
|---|---|---|---|
| 1 | 审批节点 | 蓝 | 插入后在右侧抽屉里选串行审批或并行会签，并可加触发条件 |

> 原 3 个插入项（串行审批 / 并行会签 / 条件分支）已合并为 1 个。
> 串行/会签不再靠「插入哪种节点」决定，而是在抽屉里选「审批方式」；
> 条件分支不再是一种节点，而是审批节点上的可选「触发条件」。

- 同一时刻只展开一张卡片（点其他 `+` 会切换）
- 点击画布空白处收起
- 选中后**立即插入并打开该节点的属性抽屉**

### 5.3 节点卡片

| 区域 | 内容 |
|---|---|
| 序号圆点 | ①②③…，颜色 = 审批人所属部门色 |
| 节点名 | 超长省略，hover 显示全名 |
| 操作区 | `↑` 上移 / `↓` 下移 / `×` 删除（发起与归档禁用） |

| 提醒行 | ⏰ 未处理满 Nh 提醒（仅开启提醒的节点） |

**发起 / 归档节点**不显示人员行，分别显示「发起人提交，系统自动记录」「系统自动归档」。

## 6. 流程图预览（弹窗）

点击顶部「流程图预览」打开弹窗（720px 宽，居中，带遮罩），**不再是画布下方的一段文字条**：

| 区域 | 内容 |
|---|---|
| 头部 | 流程名称 + 副标题（应用模块 + 状态 tag）+ 关闭 × |
| 摘要区 | 流程名称 / 节点总数 / 条件评估金额 / 条件结果 |
| **审批节点流转** | **引擎渲染的时间线**，与业务单据「审批详情」完全一致：节点序号圆点、状态 chip、审批人姓名 + 脱敏手机号 + 部门、提醒规则说明 |
| 触发条件求值明细 | 节点 / 条件 / 操作符 / 阈值 / 实际值 / 结果（6 列表格，带条件才有） |
| 底部 | 关闭（无其它内容，按钮右对齐） |

**条件评估金额（v1.9.0）**：弹窗底部原有的「模拟单据金额」输入框已删除 ——
配置态没有真实单据，输入一个假金额去驱动条件求值没有实际意义。
求值改为使用模块级常量 `PREVIEW_AMOUNT = 500000` 作为**演示基准值**，
摘要区对应行由「模拟金额」改名为「条件评估金额」并加灰色小字「演示基准值」标注来源，
避免读者误以为它是可编辑的真实业务输入。

**触发条件演示**（standard 流程，「总经理审批」节点带 `单据金额 > 100万` 条件）：

| 条件评估金额 | 时间线节点 |
|---|---|
| 500,000（固定演示基准值） | 提交申请 → 业务审批 → 风控财务会签 → **总经理审批（已跳过）** → 归档完成 |
| 3,000,000（仅示意，不可在界面上输入） | 提交申请 → 业务审批 → 风控财务会签 → **总经理审批（条件命中）** → 归档完成 |

## 7. 节点属性（字段清单）

**v1.6.0：抽屉内属性项按「审批方式」分支，不再按节点类型分支**

| 节点 | 抽屉内属性项（固定顺序） |
|---|---|
| 发起 / 归档（系统节点） | 只读信息卡：节点类型 + 「系统节点，属性不可编辑」 |
| **审批节点（串行）** | ① 节点名称 ② **审批方式**（单选） ③ **审批人员** ④ **触发条件**（可选·仅串行） ⑤ 提醒规则 ⑥ **审批通知**（可多选） ⑦ **通知类型**（站内信必选 + 短信） ⑧ 节点说明 |
| **审批节点（并行会签）** | ① 节点名称 ② **审批方式**（单选） ③ **会签人员** ④ 提醒规则 ⑤ **审批通知**（可多选） ⑥ **通知类型**（站内信必选 + 短信） ⑦ 节点说明（**无触发条件**） |

#### 审批方式（单选，互斥）

一个节点只能二选一，切换时人员区随之切换：

| 选项 | 数据字段 | 人员区 |
|---|---|---|
| 串行审批 | `approveMode: 'serial'` | 单选下拉（1 名审批人），自动带出该环节默认审批人 |
| 并行会签 | `approveMode: 'parallel_all'` | 多人列表（+ 添加会签人 / × 移除，至少 1 人），从单选切过来时自动把当前审批人 + 1 人填入会签名单 |

#### 触发条件（可选 · v1.8.0 收敛为**单条金额条件**）

- 总开关「按金额条件触发」，**不勾选 = 每单都执行该节点**
- 勾选后展开**一条**条件行：`单据金额`（**固定灰底标签，不可选**）+ 操作符 + 阈值
- **没有「+ 添加条件」按钮** —— 一节点最多 1 个条件，且只能是金额条件
- 「×」= 清除条件（等价于关掉总开关）
- **满足条件才执行本节点；不满足则本节点自动跳过，流程继续往下走**
- **并行会签节点不提供触发条件**，整段不渲染；从串行切到会签时已有条件会被清空
- 带条件的节点在画布上有橙色「有条件：单据金额 > xxx」标签 + 浅琥珀底色

> 相比 v1.5.0 的改动：去掉了「字段」下拉（条件类型不再可选）、去掉了「+ 添加条件」
> 与规则列表的增删（固定 1 条）。`condition` 结构仍是数组，但**长度恒 ≤ 1**，
> `field` 恒为 `'amount'`，`then` 字段不存在。

#### 审批通知（v1.8.0 新增）

本节点**审批通过后**向所选人员推送站内消息 + 短信，可多选。

| 项 | 说明 |
|---|---|
| 位置 | 抽屉内「提醒规则」**下方**、「节点说明」上方；串行与并签节点都有 |
| 控件 | 复选下拉（`.wz-dd`），触发器显示「已选 N 人：姓名、姓名」，未选时显示「请选择接收通知的人员」 |
| 选项 | 平台人员目录 16 人，**按部门分组**（业务部/风控部/财务部/法务部/仓储部/总经理/运营管理部），每行 `姓名 + 脱敏手机号` |
| 快捷 | 面板顶部「全选 / 清空」；勾选后**面板保持展开**，方便连续多选 |
| 收起 | 点抽屉内空白处收起；**下方空间不足时自动向上弹出**（`.ap-drawer-body` 是 `overflow:auto`，向下弹会被裁） |
| 存储 | `node.notify: ['u_biz_01', ...]`（人员 id 数组，可为空） |
| 画布 | 配置后节点卡片显示 `🔔 通过后通知 N 人：姓名、姓名` |
| 时间线 | 引擎 `renderTimeline` 输出「🔔 审批通过后通知：姓名、姓名（站内信）」（被跳过的节点不显示） |

#### 通知类型（v1.10.0 新增）

配置「审批通知」的**推送渠道**。只作用于审批通知，**不影响「提醒规则」**（提醒固定站内消息 + 短信）。

| 项 | 说明 |
|---|---|
| 位置 | 抽屉内「审批通知」**下方**、「节点说明」上方；串行与并签节点都有 |
| 控件 | 两行卡片式复选（`.cv-chan-box` > `.cv-chan-opt`），行间 1px 分隔线 |
| **站内信** | **默认勾选且 `disabled` 不可取消**，行尾带蓝色「必选」标记。保证审批通知有留痕 |
| **短信提醒** | 可勾选/取消，默认关闭 |
| 依赖 | 未选接收人时整个区块置灰（`.is-disabled`），提示「请先在上方选择接收通知的人员，再配置推送渠道」；选中人员后自动解除 |
| 存储 | `node.notifyChannels: ['inbox']` / `['inbox','sms']` |
| 兜底 | 引擎 `normNode` **恒定补回 `inbox`**、只认 `inbox`/`sms`、去重、按固定顺序排列 —— 前端绕过也改不掉 |
| 画布 | 节点卡片 `🔔 通过后通知 N 人：姓名、姓名（站内信、短信提醒）` |
| 时间线 | 引擎 `renderTimeline` 输出「🔔 审批通过后通知：姓名、姓名（站内信、短信提醒）」 |

> ⚠️ **站内信为什么锁死**：审批通知是「谁被知会」的证据链，取消后可能出现审批已过但无人可查的合规风险。
> 引擎层 `normNode` 强制补 `inbox`，即使有人绕过前端直接改 localStorage 也去不掉。

### 7.1 审批人员

- **来源**：`ApprovalEngine.PEOPLE` 平台人员目录（原型 Mock，接真实组织架构后只换数据源）
- **展示格式**：`完整姓名  脱敏手机号`（如 `张磊  138 0000 XXXX`）
- **存储**：节点上的 `approver: 'u_biz_01'`（人员 id）
- **节点配色**：按人员所属部门取色

### 7.2 提醒规则

```js
remind: { enabled: true, afterHours: 24 }
```

| 控件 | 说明 |
|---|---|
| 开启审批提醒（复选） | 关闭后小时数禁用，卡片与预览中的提醒行消失 |
| N 小时（1~720） | 未处理满 N 小时后推送站内消息 + 短信 |

### 7.3 会签人员

- 每人一个下拉 + 删除按钮；同一人不能重复；至少 1 人
- 新增时自动选一个尚未加入的人员

### 7.4 条件规则

| 控件 | 选项 |
|---|---|
| 字段 | 单据金额 / 业务类型 / 合同类型 / 客户等级 / 风险等级 |
| 操作符 | > ≥ < ≤ = ≠ |
| 阈值 | 数字输入 |
| 命中时追加节点 | 审批环节下拉 |

命中后自动带出该环节的**默认审批人**（`ROLES[key].defaultPerson`）。

## 13. 节点模型 v1.6.0 变更（2026-10-19）

### 13.1 为什么改

v1.5.0 及之前，业务节点有 4 种类型：`start` / `serial` / `parallel_all` / `branch`。
插节点要选「插入哪种节点」，串行和会签是两个不同节点，导致：

- 同一种审批（都是「谁来审」）被拆成两种节点类型，配置心智负担重
- `branch` 节点的 `condition[].then` 要指定「命中后追加哪个角色的节点」，
  与节点本身重复表达，条件逻辑绕
- 前端实现要分别处理 3 个渲染分支

### 13.2 现在的模型

```
start ──▶ approval ──▶ approval ──▶ archive
          │              │
          ├ approveMode  ├ approveMode
          │  = serial    │  = parallel_all
          │              └ condition[]（可选）
          └ condition[]（可选）
```

| 变更点 | 改前 | 改后 |
|---|---|---|
| 业务节点类型 | `serial` + `parallel_all` 两个 | 统一 `approval`，用 `approveMode` 区分 |
| 条件 | 独立的 `branch` 节点，`condition[].then` 指定追加角色 | `approval` 节点上的可选 `condition[]`，只决定「跑不跑」 |
| 插入选项 | 3 项（串行/会签/分支） | 1 项（审批节点） |
| 抽屉分支 | 按 `n.type` 分 3 套表单 | 按 `approveMode` 分 2 套人员区，条件区始终可见 |

### 13.3 历史数据兼容

`ApprovalEngine.normNode()` / `normFlow()` 在读取侧归一化三代历史数据，
`listFlows` / `getFlow` / `resolveFlow` 全部经过它，用户本地无需清理：

| 历史类型 | 归一化结果 |
|---|---|
| `serial` | `approval` + `approveMode='serial'` |
| `parallel_all` | `approval` + `approveMode='parallel_all'` |
| `serial` + `auto:true` | `archive` |
| `branch` | 按 `condition[].then` 里的角色**展开成多个 `approval` 节点**，每个继承同一条条件（去掉 `then`） |
| `condition[].then` | 一律丢弃（新模型条件不负责追加节点） |

> `standard` 内置模板里的「金额分支」节点已直接改写为
> 「总经理审批」审批节点 + `单据金额 > 100万` 触发条件，行为与改前一致。

## 14. 步骤 1 容器底板（v1.7.0）

### 14.1 问题

v1.6.0 及之前，步骤 1「基础信息」的表单字段**直接浮在 `.page-body` 的灰底上**，
没有白色底板，与全站其它页面不一致：

| 页面类型 | 容器惯例 |
|---|---|

| **v1.6.0 的步骤 1** | ❌ 无底板 |

> 注意：`.page-body` 的 `--bg-page` 底色**没有丢**，两页实测同为 `rgb(248,250,252)`。
> 丢的是「白色内容底板」这一层。

### 14.2 改法

步骤 1 外层套 `cp-panel wz-panel`，内部分两个 `cp-block`：

```
.cp-panel.wz-panel        max-width: 860px; margin: 20px auto 0
  ├ .cp-block             padding: 18px 24px → .wz-form（max-width 760px 居中）
  └ .cp-block.wz-panel-foot  padding: 18px 24px → 「下一步：流程设计」按钮居中
```

实测与参照页 `warehouse-inbound.html` 的 `cp-panel` 逐项一致：

| 属性 | 参照页 `cp-panel` | 本页 `.wz-panel` |
|---|---|---|
| `background` | `rgb(255, 255, 255)` | `rgb(255, 255, 255)` |
| `border-radius` | `12px` | `12px` |
| `border-top` | `rgb(226, 232, 240) 1px` | `rgb(226, 232, 240) 1px` |
| `overflow` | `hidden` | `hidden` |

差异只有**宽度**：列表页面板满宽，表单卡片取 860px 居中（内容区 1380px 时左右各留 260px 灰底），
避免 760px 的表单字段在大面板里左右空一大片。

步骤 2「流程设计」的画布是**独立容器**（`.cv-body` / `.cv-canvas`，v1.6.0 的整页铺满逻辑），
不受本节影响。
